# WB-STD-003 «Шаблоны устройств для драйвера wb-mqtt-serial»

**Версия 1.4. Дата: 2026-09-07.**

> Документ содержит только правила, специфичные для шаблонов wb-mqtt-serial:
>
> - правила формирования идентификаторов MQTT-топиков — в [WB-STD-001](<WB-STD-001 Идентификаторы MQTT-топиков в экосистеме Wiren Board.md>);
> - правила оформления UI-текстов и переводов — в [WB-STD-002](<WB-STD-002 Стиль текстов в пользовательском интерфейсе Wiren Board.md>);
> - правила публичных MQTT-соглашений — в [Wiren Board MQTT Conventions](https://github.com/wirenboard/conventions).
>
> Документ согласован с указанными источниками и не противоречит им.

---

## 1. Область применения

Стандарт устанавливает правила формирования шаблонов устройств для драйвера Wiren Board `wb-mqtt-serial`. Шаблон — JSON-файл, описывающий устройство, его параметры настройки и каналы, публикуемые драйвером в MQTT.

Стандарт применяется ко всем новым шаблонам устройств Wiren Board. К партнёрским и пользовательским шаблонам — рекомендательно.

Существующие шаблоны переводятся на новые правила постепенно, по отдельному плану миграции.

---

## 2. Принципы

Шаблон должен быть:

- **однозначно интерпретируемым** драйвером, валидатором и линтером;
- **понятным конечному пользователю** в веб-конфигураторе (вместе со стилем по WB-STD-002);
- **миграционно совместимым** — при выпуске новой версии устройства имена сохраняемых сущностей не меняются (см. §10.2).

---

## 3. Структура шаблона

Шаблон — JSON-документ, соответствующий JSON-схеме `wb-mqtt-serial-device-template.schema.json`. Схема определяет обязательные и допустимые поля, типы значений и базовую структуру.

Настоящий стандарт устанавливает требования сверх схемы — содержательные правила формирования значений, канонические имена и стиль.

**Верхний уровень шаблона:**

```jsonc
{
    "device_type": "...",       // обязательно; он же ключ перевода имени шаблона (см. §4.4, §4.3)
    "group": "...",             // идентификатор группы устройств в каталоге (см. groups.json в репозитории wb-mqtt-serial)
    "hw": [ ... ],              // привязка к устройству / прошивке (см. §4.6)
    "device": {
        "name": "...",          // отображаемое имя устройства = маркировка (см. §4.4)
        "id": "...",            // идентификатор устройства, см. WB-STD-001
        "translations": { ... }, // переводы (см. §4.3, WB-STD-002)
        "groups": [ ... ],      // см. §5
        "parameters": [ ... ],  // см. §6
        "channels": [ ... ],    // см. §7
        "setup": [ ... ]        // опционально, см. §9.7
    }
}
```

Поля `device.setup`, `device.translations` — опциональны. Поле `hw[]` опционально в общем случае, но **обязательно для шаблонов устройств Wiren Board** — для сопоставления по `signature`; поле `fw` внутри `hw[]` опционально и задаёт привязку к версии прошивки (см. §4.6, §10.3).

Порядок полей в JSON стандартом не нормируется.

## 4. Идентификаторы, стиль текстов и канонические имена

### 4.1 Идентификаторы

Правила формирования идентификаторов (каналов, параметров, групп, `device.id`) определяются WB-STD-001 «Идентификаторы MQTT-топиков в экосистеме Wiren Board».

Кратко: алфавит `[a-z0-9_]`, snake_case, не более 64 символов, регулярное выражение `^[a-z][a-z0-9]*(_[a-z0-9]+)*$`; рекомендация — не более четырёх смысловых единиц (WB-STD-001 §2.3).

### 4.2 Стиль текстов

Правила оформления текстов, видимых пользователю (имена сущностей в `translations`, `description`, значения `enum_titles`), определяются WB-STD-002 «Стиль текстов в пользовательском интерфейсе Wiren Board».

Кратко: ASCII-кавычки и дефис; «е» вместо «ё»; точка как десятичный разделитель; EN — Title Case, RU — Sentence case; аббревиатуры заглавными; единицы в круглых скобках после названия и не в id; описания — короткие, без точки в конце.

### 4.3 Двуязычность и переводы

Многоязычные тексты (имена шаблона, групп, каналов, параметров; описания; значения `enum_titles`) реализуются через секцию `device.translations`:

```jsonc
"device": {
    "translations": {
        "en": {
            "<key>": "English string",
            ...
        },
        "ru": {
            "<key>": "Русская строка",
            ...
        }
    }
}
```

Действует **единая модель «идентификатор-как-ключ»**: ключом перевода служит идентификатор самой сущности, а строки — на обоих языках — задаются в `translations` по этому ключу. Отображаемый текст в секциях не пишется напрямую.

- Для **каналов** идентификатор помещается в поле `name`, поле `id` не используется (см. §7.1).
- Для **параметров** и **групп** ключ перевода — их `id` (см. §5.2, §6.1).
- Для **шаблона в каталоге** ключ перевода — `device_type` (см. §4.4).

Поле `title` — у шаблона, групп и параметров — не задаётся: идентификатор служит ключом перевода, пока `title` отсутствует, а при наличии `title` ключом остаётся его значение. Поэтому шаблоны, ещё не переведённые на эту модель ключей, продолжают работать без изменений, но в новых шаблонах `title` не пишется. Перевод по идентификатору поддерживается начиная с wb-mqtt-serial 2.272.0 и wb-mqtt-homeui 2.251.0.

Имя устройства `device.name` в модель не входит: это литеральная отображаемая строка — маркировка устройства (см. §4.4), переводы на неё не распространяются.

Обе языковые версии (`en` и `ru`) задаются явно — при отсутствии перевода интерфейс показывает сам ключ.

**Паттерны ключей переводов** (для сущности с идентификатором `<id>`):

| Текст | Ключ перевода |
| --- | --- |
| Имя группы или параметра | `<id>` |
| Имя канала | значение поля `name` |
| Имя шаблона в каталоге | значение поля `device_type` |
| `description` параметра/канала | `<id>_description` |
| `enum_titles[N]` (N — индекс с 0, как в массиве `enum_titles`) | `<id>_enum_<N>` |

Пример:

```jsonc
{
    "device_type": "wb-mr6c-v3",
    "device": {
        "translations": {
            "en": { "wb-mr6c-v3": "WB-MR6C v.3 (6-channel relay module)" },
            "ru": { "wb-mr6c-v3": "WB-MR6C v.3 (6-канальный модуль реле)" }
        }
    }
}
```

Ранее допускавшаяся модель «английская-строка-как-ключ» (английская строка служила и текстом, и ключом) **больше не применяется**: смена английского текста рвала связь с русским переводом. Даже короткие подписи задаются через идентификатор — `g_general` с переводами `{en: "General", ru: "Общее"}`, а не строкой `"General"` напрямую.

### 4.4 Поля устройства

Идентификация и отображение устройства в шаблоне задаются тремя полями.

| Поле | Описание и требования | Пример |
| --- | --- | --- |
| `device_type` | Машинный идентификатор семейства шаблона; привязка пользовательской конфигурации (`wb-mqtt-serial.conf`) к шаблону.<br>Формально: `device_type = basename(имя_файла)` без расширения (`.json` / `.json.jinja`), без префикса `config-` и без суффикса `-deprecated`. Суффиксы `-fw<N.M>` (§10.3) и `-tpl<N>` (§10.4) присутствуют и в `device_type`, и в имени файла.<br>Алфавит для новых шаблонов — строчные `[a-z0-9._-]`; legacy-значения (пробелы, заглавные буквы) сохраняются до миграции.<br>**Имя шаблона в каталоге.** `device_type` служит ключом перевода имени шаблона в каталоге устройств веб-конфигуратора; отображаемые строки задаются в `device.translations` (§4.3) для обоих языков. Имя обычно длиннее `device.name`: содержит модель и краткое пояснение функционала. | `wb-mr6c-v3`<br>`wb-example-fw2.0`<br>`wb-mr6c-v3-tpl1`<br><br>`translations.en["wb-mr6c-v3"]`: `WB-MR6C v.3 (6-channel relay with internal power supply)`<br>`translations.ru["wb-mr6c-v3"]`: `WB-MR6C v.3 (6-канальный модуль реле с внутренним блоком питания)` |
| `device.name` | Отображаемое имя устройства в UI и в метаключе `/devices/.../meta/name` (драйвер по умолчанию добавляет к нему номер устройства на шине). Должно совпадать с маркировкой устройства, включая регистр и пунктуацию. Не переводится: единая строка для всех языков интерфейса, секция `translations` на неё не действует (WB-STD-002 §8.1). Допускаются любые символы маркировки, включая кириллицу (`ОВЕН МВ110`) и специальные символы (`Carel µC2SE`); ограничения WB-STD-001 относятся к `device.id`, а не к `device.name`.<br>**Бренд в имени.** Если маркировка устройства уже содержит префикс бренда (`WB-MR6C v.3`, `WB-LED`) — бренд в имени не дублируется. Если маркировка бренд не содержит — он указывается явно перед моделью через пробел (`ОВЕН МВ110`, `EKF AVR-01`). | `WB-MR6C v.3`<br>`ОВЕН МВ110`<br>`EKF AVR-01` |
| `device.id` | Основа MQTT-идентификатора устройства: по умолчанию драйвер публикует устройство как `/devices/<device.id>_<slave_id>/...`; поле `id` в конфигурации пользователя переопределяет идентификатор целиком. Для новых шаблонов формируется по правилам WB-STD-001 (snake_case, `[a-z0-9_]`). Для существующих шаблонов остаётся без изменений. После попадания шаблона в `master` не меняется (§10.2). | `wb_mr6c_v3` |

**Шаблоны, обслуживающие несколько моделей одного семейства.** Для мультимодельных шаблонов:

- `device_type` формируется как `<модель1>_<модель2>_<…>`, где каждый `<модельN>` — полный идентификатор модели (включая префикс `wb-`). Разделитель моделей — `_`, чтобы отличать границы моделей от внутрисловного дефиса в каждом идентификаторе модели.<br>Пример: `wb-mr3lv_wb-mr3hv_wb-mrwl3`.
- имя шаблона (в `translations.en`/`ru` по ключу `device_type`) перечисляет все модели через запятую, с пояснением функционала в скобках.<br>Пример: `WB-MR3LV, WB-MR3HV, WB-MRWL3 (3-channel relay modules)`.

### 4.5 Канонические имена сущностей

Идентификаторы и переводы для каналов, многократно встречающихся в WB-шаблонах (служебные каналы, входы/выходы, счётчики, трёхфазные величины, климатические каналы, аварии), определяются **WB-STD-001 §6 «Канонические имена»**.

Канонические идентификаторы стандартных групп шаблона (`g_general`, `g_hw_info`, `g_in<N>`, `g_outputs`, `g_safety` и др.) и их подгрупп (`gg_in<N>_*`) — Приложение А настоящего стандарта.

Если сущность присутствует в канонических реестрах, применяется каноническая форма; альтернативные формы не допускаются.

### 4.6 Блок `hw[]`

Массив `hw[]` верхнего уровня привязывает шаблон к физическим устройствам и/или версиям прошивки. Каждый элемент описывает одно сочетание «сигнатура устройства + минимальная версия прошивки».

| Поле | Тип | Назначение |
| --- | --- | --- |
| `signature` | строка | Сигнатура (модель) устройства, возвращаемая прошивкой при сканировании. Используется драйвером для автоматического сопоставления физического устройства с шаблоном. |
| `fw` | строка | Минимальная версия прошивки в формате `"N.M.K"` (без операторов сравнения и диапазонов; см. §9.4). Шаблон применяется к устройствам с прошивкой не ниже указанной. Поле опционально: базовый шаблон семейства задаёт только `signature`. |

**Откуда драйвер читает эти значения** (общие регистры прошивок Wiren Board, Modbus holding):

| Значение | Регистр | Формат |
| --- | --- | --- |
| Модель / сигнатура (`signature`) | `200` | строка (6 регистров; расширенная форма — 20) |
| Версия прошивки (для сравнения с `fw`) | `250` | строка (16 регистров) |
| Сигнатура прошивки (для проверки при обновлении, не для сопоставления шаблона) | `290` | строка (12 регистров) |

`hw[].signature` сопоставляется со строкой модели из регистра `200`; `hw[].fw` — с версией прошивки из регистра `250`.

**Правило сопоставления.** При сканировании устройств драйвер выбирает шаблон с подходящей сигнатурой и максимальным `hw[].fw`, не превышающим фактическую версию прошивки устройства (см. §10.3).

**Обязательность.** Для шаблонов устройств Wiren Board блок `hw[]` обязателен — он обеспечивает сопоставление по сигнатуре. Поле `fw` внутри `hw[]` по схеме опционально (обязательна только `signature`) и задаёт привязку к версии прошивки (§10.3). Для партнёрских и пользовательских шаблонов блок опционален.

```jsonc
"hw": [
    {
        "signature": "WB-LED",
        "fw": "3.8.0"
    }
]
```

## 5. Группы (`groups[]`)

Группы определяют иерархию отображения параметров и каналов в UI веб-конфигуратора.

### 5.1 Иерархия и префиксы

Допускается до трёх уровней вложенности. Префикс идентификатора группы маркирует уровень:

| Уровень | Префикс | Пример |
| --- | --- | --- |
| Корневой | `g_` | `g_general`, `g_hw_info`, `g_in1` |
| Второй | `gg_` | `gg_in1_channels`, `gg_in1_press_params` |
| Третий | `ggg_` | `ggg_safety_mode_ch_1_2` |

### 5.2 Поля группы

Корневая группа (без родителя) — поле `group` опускается:

```jsonc
{
    "id": "g_general",
    "ui_options": {
        "wb": {
            "disable_title": false
        }
    }
}
```

Подгруппа — `group` указывает id родительской группы:

```jsonc
{
    "id": "gg_in1_channels",
    "group": "g_in1"
}
```

Ключом перевода служит `id`, поле `title` не задаётся (до версии 1.4 стандарта оно требовалось, см. §4.3). Отображаемые имена группы задаются в `device.translations` по этому ключу, стиль — по WB-STD-002. По схеме `wb-mqtt-serial-device-template.schema.json` поле `group` имеет тип `string`; литеральный `null` недопустим — для корневой группы поле опускается.

### 5.3 Канонические группы и подгруппы

См. Приложение А. При наличии соответствующей сущности её следует помещать в каноническую группу (или подгруппу).

## 6. Параметры (`parameters[]`)

Параметры — поля настройки устройства, выставляемые пользователем в веб-конфигураторе при создании конфигурации (записываются в устройство при старте драйвера).

### 6.1 Основные поля

```jsonc
{
    "id": "baud_rate",                          // он же ключ перевода имени параметра (§4.3)
    "description": "baud_rate_description",     // опционально; ключ перевода — <id>_description (§4.3)
    "address": 123,                             // см. §8
    "reg_type": "holding",                      // см. §8
    "format": "u16",                            // см. §8
    "default": 96,
    "enum": [96, 192, 384, 576, 1152],
    "enum_titles": ["9600", "19200", ...],
    "group": "g_general",
    "condition": "...",                         // см. §9.3
    "fw": "1.23.0"                              // см. §9.4 (минимальная версия)
}
```

**Поле `readonly`** (`true` / `false`) — параметр не привязан к регистрам устройства: адресные поля игнорируются, значение живёт только в конфигурации. Применяется для организации настроек в веб-конфигураторе: обычно такой параметр управляет `condition` других элементов (например, выбор модификации устройства или схемы подключения).

### 6.2 Идентификаторы параметров

Для `parameters[].id` допустимы три формы:

| Форма | Когда применять | Пример |
| --- | --- | --- |
| **Описательный snake_case** | Технические/коммуникационные параметры (скорость обмена, таймауты, общие режимы) и параметры устройств, где смысл выражается осмысленным словом | `baud_rate`, `safety_timer`, `disable_indication` |
| **`p<N>` — позиционный** | Устройства с десятками параметров без естественных имён и без панели с кодами | `p1`, `p2`, …, `p47` |
| **Panel-код** | Устройства с этикеточными кодами параметров (частотные преобразователи, ПЛК), где код — общеизвестная сущность из документации | `f0_04`, `pn_01_03`, `a01` |

**Правило выбора формы в шаблоне:**

- **Описательная форма** допускается всегда — для технических/коммуникационных параметров (`baud_rate`, `slave_id_offset`, таймауты, общие режимы), для которых описательное имя естественно. Эти параметры присутствуют в шаблоне в описательной форме независимо от того, какая форма выбрана для основной массы.
- **Для основной массы device-specific параметров** (специфика конкретного семейства устройств — режимы работы, настройки функционала) выбирается **одна** форма: либо `p<N>`, либо panel-код. Смешивать `p<N>` и panel-код в одном шаблоне для основной массы не допускается.

Единицы измерения в `id` параметра не указываются (WB-STD-001 §2.4): они указываются в названии параметра в круглых скобках (WB-STD-002 §5).

Пример комбинации в шаблоне частотного преобразователя:

| id | Форма | Назначение |
| --- | --- | --- |
| `baud_rate` | описательная | скорость обмена RS-485 |
| `safety_timer` | описательная | таймер безопасного режима |
| `f0_04` | panel-код | параметр панели F0.04 (основная масса) |
| `f0_05` | panel-код | параметр панели F0.05 |
| `pn_01_03` | panel-код | параметр панели Pn-01.03 |

### 6.3 Нормализация panel-кодов

Panel-код устройства часто содержит точку или дефис (например, `F0.04`, `Pn-01.03`). В id параметра он приводится к нормализованной форме:

- символы `.`, `-`, `:` заменяются на `_`;
- буквы приводятся к нижнему регистру;
- ведущие нули не убираются;
- если после нормализации код начинается с цифры, добавляется префикс `p`: `00-01` → `p00_01`.

Примеры:

| Panel-код на устройстве | id в шаблоне |
| --- | --- |
| `F0.04` | `f0_04` |
| `Pn-01.03` | `pn_01_03` |
| `A01` | `a01` |

В отображаемом тексте (в `translations` по ключу `id`) panel-код сохраняется в исходной маркировке: `"f0_04": "F0.04 - Frequency Setting"`.

### 6.4 Типы значений

| Тип параметра | Признак |
| --- | --- |
| Целое число | `format: u8 / s8 / u16 / s16 / u24 / s24 / u32 / s32 / u64 / s64` |
| Число с плавающей точкой | `format: float / double` |
| Перечислимое | поле `enum`, опционально `enum_titles` |
| Логическое (двоичное) | `format: u8` + `enum: [0, 1]` + `enum_titles` |
| BCD | `format: bcd8 / bcd16 / bcd24 / bcd32` |
| Строка | `format: string / string8` + `string_data_size`; одиночный ASCII-символ — `format: char8` |

Таблица выше — ориентир для выбора формата под тип значения. Перечень допустимых значений `format` и их размеры — в §8.3 (источник — enum схемы).

### 6.5 Группа параметра

`parameters[].group` — id группы (см. §5), в которой параметр отображается. Если не указано — корень.

## 7. Каналы (`channels[]`)

Каналы устройства публикуются драйвером в MQTT и отображаются пользователю в реальном времени.

### 7.1 Имя канала (`name`)

Канал именуется **одним полем `name`**, в которое помещается канонический идентификатор канала по WB-STD-001 §6 (`<channel_id>`, snake_case). Поле `id` в новых шаблонах **не используется**.

| Поле | Назначение | Правила |
| --- | --- | --- |
| `name` | Идентификатор канала. Драйвер формирует из него топик `/devices/<device.id>_<slave_id>/controls/<name>` (см. §4.4) и использует как ключ перевода. | snake_case, канон WB-STD-001 §6 |

Отображаемые имена (EN/RU) задаются в `device.translations` по ключу, равному `name` (§4.3). Один идентификатор служит и топиком, и ключом перевода — без дублирования `id` / `name`.

> **Сопоставление с таблицами WB-STD-001 §6.** Значение из колонки `id` таблиц §6 помещается в JSON-поле `name` канала. Колонки `name (EN)` и `RU перевод` из §6 — это отображаемые строки; они идут в `device.translations` по ключу, равному этому идентификатору (не в поле `name`).

Поле `id`, если задано, переопределяет топик; в новых шаблонах не используется и оставлено для совместимости с legacy-шаблонами, где `name` содержал человекочитаемую строку.

### 7.2 Основные поля канала

```jsonc
{
    "name": "u_rms_l1",                 // идентификатор канала = топик + ключ перевода (§7.1)
    "reg_type": "input",                // см. §8
    "address": 12,                      // см. §8
    "format": "u16",                    // см. §8
    "scale": 0.01,                      // опционально
    "offset": 0,                        // опционально
    "units": "V",                       // словарь единиц — Conventions §3 (см. WB-STD-001 §2.1)
    "min": 0,
    "max": 250,
    "round_to": 0.01,
    "readonly": true,                   // true или false
    "sporadic": true,                   // см. §7.4
    "enabled": false,                   // см. ниже
    "error_value": 65535,               // см. §8.6
    "group": "g_general",               // см. §5, Приложение А
    "condition": "...",                 // см. §9.3
    "fw": "1.20.0"                      // см. §9.4 (минимальная версия)
}
```

Поле `write_address` (для каналов с разными адресами чтения и записи) применимо только к writable-каналам — не к `readonly`; см. §9.5.

(поле `type` опущено — подразумевается `value`; см. §7.3).

**Поле `enabled`** (`true` / `false`) — управляет тем, опрашивает ли драйвер канал по умолчанию. Для новых каналов, добавляемых в существующий шаблон после попадания в `master`, обязательно указывается `"enabled": false` (см. §10.2): канал виден пользователю, но активируется им явно.

### 7.3 Типы каналов

Типы — из конвенции [Wiren Board MQTT Conventions §3](https://github.com/wirenboard/conventions#3-control-types) (значения метаключа `meta/type`).

**Функциональные типы.** Применяются по назначению:

| Тип | Смысл |
| --- | --- |
| `value` | Числовое значение общего назначения. **Значение по умолчанию**; поле `type` для таких каналов опускается. Применяется в сочетании с `units` для физических величин |
| `switch` | Двухпозиционный переключатель (0/1) |
| `pushbutton` | Нажимная кнопка (без состояния) |
| `range` | Целочисленный диапазон с `min`/`max` |
| `text` | Произвольный текст |
| `rgb` | Цвет в формате `R;G;B` |
| `wo-switch` | Переключатель только для записи |
| `alarm` | Двоичный индикатор тревоги (0/1) |
| `unixtime` | Время в формате Unix-времени |
| `w1-id` | Идентификатор Dallas 1-Wire |

**Специфические физические типы (deprecated).** Часть значений `type` (`temperature`, `voltage`, `power`, `pressure` и др.) помечена в схеме устаревшими — суффикс `(deprecated, use value with units)` в `enum_titles`. Полный перечень — в enum схемы (`wb-mqtt-serial-confed-common.schema.json`); в новых шаблонах эти типы не применяются.

Множество валидных значений `type` — enum схемы (функциональные + deprecated). Любые иные значения (например, `energy_power`) — невалидны.

**Правило для новых шаблонов.** Для физических величин поле `type` опускается (подразумевается `value`); единица измерения задаётся полем `units` по словарю единиц конвенции (Wiren Board MQTT Conventions §3, подраздел «Units»).

Пример канала температуры (канонический служебный канал `t_mcu`, см. WB-STD-001 §6.1):

```jsonc
{
    "name": "t_mcu",
    "reg_type": "input",
    "address": 124,
    "format": "s16",
    "scale": 0.1,
    "units": "deg C",
    "group": "g_hw_info"
}
```

(поле `type` опущено — подразумевается `value`).

### 7.4 Спорадические каналы

Поле `sporadic: true` указывает драйверу использовать Быстрый Modbus для опроса канала; значение публикуется только при наличии события на стороне устройства. Требуется поддержка со стороны прошивки.

### 7.5 Группа канала

`channels[].group` — id группы (см. §5), в которой канал отображается.

## 8. Адресация и форматы значений

### 8.1 `reg_type`

Нормативный перечень значений `reg_type` — enum JSON-схемы (`wb-mqtt-serial-confed-common.schema.json`). Таблица ниже — иллюстративная, не исчерпывающая; наиболее употребительные:

| Значение | Назначение |
| --- | --- |
| `holding` | Modbus holding registers (читать/писать) |
| `input` | Modbus input registers (только чтение) |
| `coil` | Modbus coils (битовые, читать/писать) |
| `discrete` | Modbus discrete inputs (битовые, только чтение) |
| `press_counter` | Регистр счётчика нажатий (WB-специфика) |

Полный набор (включая `holding_single`, `holding_multi`, `direct`, `relay`, `param`, `item_*`, `obis_*` и др.) определяется схемой.

### 8.2 `address`

Адрес регистра, число или строка. Поддерживаемые формы:

- целое число: `123`;
- шестнадцатеричное в строке: `"0x7B"`;
- битовое: `"<reg>:<bit_offset>:<bit_width>"` (см. §9.1).

### 8.3 `format`

Множество допустимых значений `format` — `format.enum` JSON-схемы (`wb-mqtt-serial-confed-common.schema.json`). Таблица ниже — нормативная WB-надстройка: размер каждого формата в 16-битных регистрах и семантика (этих данных в схеме нет).

| Значение | Размер, 16-битных регистров | Описание |
| --- | --- | --- |
| `u8`, `s8` | 1 | 8-битное целое (без знака / со знаком) |
| `u16`, `s16` | 1 | 16-битное целое |
| `u24`, `s24` | 2 | 24-битное целое |
| `u32`, `s32` | 2 | 32-битное целое |
| `u64`, `s64` | 4 | 64-битное целое |
| `float` | 2 | IEEE 754 32-bit |
| `double` | 4 | IEEE 754 64-bit |
| `bcd8` | 1 | 8-битный BCD |
| `bcd16` | 1 | 16-битный BCD |
| `bcd24` | 2 | 24-битный BCD |
| `bcd32` | 2 | 32-битный BCD |
| `char8` | 1 | один ASCII-символ |
| `string` | определяется `string_data_size` | строка |
| `string8` | определяется `string_data_size` | строка с 8-битной кодировкой |

### 8.4 `word_order`

Для многорегистровых форматов порядок слов задаётся полем `word_order`, порядок байт — полем `byte_order`; допустимые значения (`big_endian` / `little_endian`) — в enum JSON-схемы. По умолчанию `big_endian` (MSB first). Конкретное значение уточняется по даташиту устройства.

### 8.5 `scale` и `offset`

Преобразование сырого значения регистра в физическую величину:

```
displayed = raw * scale + offset
```

`scale` — обычно степень десяти (`0.1`, `0.01`, `0.001`), реже произвольное.

### 8.6 `error_value`

Маркерное «сырое» значение регистра, обозначающее, что устройство не смогло измерить величину или сообщает об ошибке (например, `0xFFFF` для `u16`, `0x8000` для `s16`). При получении этого значения драйвер не публикует число в MQTT, а помечает канал ошибкой (метаключ `meta/error`).

Значение задаётся в исходном (до `scale`/`offset`) виде, в формате `format` канала.

## 9. Специальные случаи

### 9.1 Битовые поля

Битовый канал/параметр имеет адрес в формате `"<reg>:<bit_offset>:<bit_width>"` (три компонента, разделённые двоеточиями). Один бит задаётся шириной `1`.

```jsonc
{
    "name": "alarm_1",
    "reg_type": "input",
    "address": "0x100:5:1",
    "type": "alarm"
},
{
    "name": "error",
    "reg_type": "input",
    "address": "0x100:0:4"
}
```

Bit offset считается от младшего бита. Поле не должно пересекать границы регистра.

Форма битового адреса валидируется паттерном `address.pattern` JSON-схемы. Семантика (в схеме её нет): компоненты `offset` и `width` указываются либо оба, либо ни одного — форма `"<reg>:<bit_offset>"` без `<bit_width>` недопустима.

### 9.2 Многорегистровые параметры

Для `format` размером > 1 регистра поле `address` указывает первый регистр. Порядок слов определяется `word_order`.

```jsonc
{
    "name": "e_ap_total",
    "reg_type": "input",
    "address": 1024,
    "format": "u32",
    "word_order": "big_endian",
    "units": "kWh"
}
```

(поле `type` опущено — подразумевается `value`; единицы измерения — по словарю Wiren Board MQTT Conventions §3).

### 9.3 Условия (`condition`)

Поле `condition` — логическое выражение, ссылающееся на id параметров. Если выражение возвращает `false`, элемент не активен (скрывается, не опрашивается, не записывается).

```jsonc
{
    "name": "di_1",
    "reg_type": "discrete",
    "address": 0,
    "type": "switch",
    "group": "gg_in1_channels",
    "condition": "encoder_1_mode==0",
    "sporadic": true
}
```

**Грамматика.** Поддерживается **ограниченное JS-подобное выражение** (не произвольный JavaScript). Парсер драйвера (`src/expression_evaluator.{h,cpp}`) принимает:

- сравнения: `==`, `!=`, `>`, `<`, `>=`, `<=`;
- логические операторы: `&&`, `||`;
- скобки для группировки: `(`, `)`;
- целочисленные литералы (с возможным ведущим `-`);
- идентификаторы параметров (snake_case);
- единственную функцию `isDefined(<id>)` — `true`, если параметр с указанным `id` определён в текущей конфигурации.

Любые иные конструкции JS — унарное отрицание `!`, арифметика, строки, тернарный оператор, любые другие функции — **не поддерживаются**.

Идентификаторы в выражении — id параметров (не каналов и не топиков); должны существовать в `parameters[]` шаблона.

Пробелы в выражении не допускаются (лексер не пропускает пробельных символов).

Примеры:

```jsonc
"condition": "encoder_1_mode==0"
"condition": "isDefined(safety_mode_source)&&safety_mode_source!=1"
"condition": "(mode==1)||(mode==3)"
```

### 9.4 Зависимость от прошивки (`fw`)

Поле `fw` — строка с **минимальной** версией прошивки, начиная с которой элемент поддерживается. Указывается как чистая версия (`"1.2.3"`), без операторов сравнения и без диапазонов. Если прошивка устройства ниже — элемент не активен. Отсутствие поля означает поддержку любой версии прошивки.

```jsonc
{
    "name": "v_mcu",
    "fw": "1.20.0",
    ...
}
```

Если в `parameters[]` есть несколько записей с одним и тем же `id` (например, варианты под разные `condition`), значение `fw` у них должно совпадать. Исключение — **fw-варианты**: когда новая прошивка только расширяет набор допустимых значений параметра, форк шаблона (§10.3) не нужен, параметр объявляется ещё раз с тем же `id` и `condition`, но с `fw` новой прошивки.

### 9.5 Разделённый адрес записи (`write_address`)

Применяется, когда регистр имеет разные адреса для чтения и записи. Поле `address` указывает регистр чтения, `write_address` — регистр записи:

```jsonc
{
    "name": "do_k1",
    "reg_type": "holding",
    "address": 100,
    "write_address": 200,
    "type": "switch"
}
```

### 9.6 Нестандартные бинарные значения (`on_value` / `off_value`)

Применяется для двухпозиционных каналов, у которых «включено»/«выключено» соответствуют не `1`/`0`, а произвольным значениям регистра (например, словам-маркерам команды). Механизм независим от `write_address`:

```jsonc
{
    "name": "door_lock",
    "reg_type": "holding",
    "address": 50,
    "on_value": "0x00a5",
    "off_value": "0x005a",
    "type": "switch"
}
```

`on_value`/`off_value` и `write_address` могут применяться независимо или совместно.

### 9.7 Setup-операции (`setup[]`)

Массив операций, выполняемых драйвером при подключении устройства (запись начальных значений в регистры). Используется для устройств, требующих инициализации.

**Рекомендация.** Предпочтительный способ задания настроек устройства — `parameters[]` (§6): значение выставляется пользователем явно в веб-конфигураторе и хранится в его конфигурации. `setup[]` применяется как крайний случай — когда регистр обязательно нужно проинициализировать при подключении устройства, но не нужно отображать в интерфейсе.

В элементе `setup` поддерживается поле `condition` (см. §9.3) — операция выполняется только если выражение истинно (т. е. зависит от значений `parameters[]`). Поле `fw` в `setup` не поддерживается — операции выполняются всегда, независимо от версии прошивки.

```jsonc
"setup": [
    {
        "title": "Set Modbus delay",
        "address": 200,
        "reg_type": "holding",
        "value": 5
    },
    {
        "title": "Enable curtain mode",
        "address": 1280,
        "reg_type": "holding",
        "value": 1,
        "condition": "curtain1_mode==1"
    }
]
```

## 10. Имя файла и версионирование шаблонов

### 10.1 Имя файла

Имя файла шаблона строится из `device_type` с добавлением префикса `config-` и расширения `.json` или `.json.jinja`. Например:

- `device_type: "wb-mr6c-v3"` → `config-wb-mr6c-v3.json.jinja`
- `device_type: "wb-example-fw2.0"` → `config-wb-example-fw2.0.json.jinja`

Расширение `.json` используется для статических JSON-шаблонов, `.json.jinja` — для шаблонов, рендеримых через Jinja2 (правила выбора расширения — см. §10.5).

Поддерживаемые Jinja-механизмы и доступные переменные определяются драйвером `wb-mqtt-serial`; их описание — в документации драйвера (вне области настоящего стандарта).

Для шаблонов, привязанных к конкретной версии прошивки, и для deprecated-шаблонов имя файла получает дополнительные суффиксы — см. §10.3 и §10.4.

### 10.2 Обратная совместимость

При выпуске новой ревизии устройства, не нарушающей обратной совместимости, изменения вносятся в существующий шаблон.

**Что нельзя изменять после попадания шаблона в `master`:**

- `name` каналов — формирует топик `/controls/<name>` (§7.1); изменение или удаление запрещено, допускается только добавление новых каналов;
- `id` параметров — изменение или удаление запрещено; допускается только добавление новых;
- `device.id` — не меняется: он фиксирует имя MQTT-устройства;
- `device_type` — не меняется (сохраняется в `wb-mqtt-serial.conf` для привязки к шаблону).

**Что можно изменять:**

- имя файла шаблона — в пределах формулы §4.4 (смена расширения, добавление суффикса `-deprecated`), иначе нарушится тождество `device_type = basename(имя_файла)`;
- имена и `description` каналов, групп, параметров (отображаемый текст — в `device.translations`);
- `device.name`;
- содержимое `device.translations`;
- `group` каналов и параметров (логическая группировка в UI);
- `id` групп (включая префикс уровня `g_`/`gg_`/`ggg_`) — переуровневание UI допустимо; синхронно обновляются ссылки `group: "..."` в каналах и параметрах, а также ключи группы в `translations` (§4.3).

Эти поля влияют только на отображение, не на топики и не на пользовательские конфиги.

**Добавление новых элементов в существующий шаблон.**

Допускается:
- добавление нового канала или параметра;
- добавление нового варианта параметра (новой строки в `parameters[]` с тем же `id`, но с другим `condition`) — без изменения существующих `condition`;
- расширение набора допустимых значений существующего параметра новой прошивкой — новым fw-вариантом (§9.4), без изменения существующей строки.

При любом таком добавлении:
- у нового элемента **обязательно** указывается поле `fw` — минимальная версия прошивки, с которой элемент доступен (§9.4);
- новый канал по умолчанию имеет `"enabled": false` (пользователь активирует его сам).

**Запрещено в рамках совместимой эволюции:** изменение существующих `condition`, изменение или удаление существующих значений `enum`, сужение числового диапазона, удаление каналов или параметров. Для таких изменений см. §10.3.

### 10.3 Шаблон для конкретной версии прошивки

Применяется, когда выпускается новая ревизия устройства с прошивкой, в которой регистровая карта или поведение существенно изменились, и часть шаблона должна работать **только** на этой и более поздних прошивках.

**Когда правим существующий шаблон, а когда создаём новый:**

| Изменение | Куда |
| --- | --- |
| Добавить новый канал или параметр | в существующий шаблон (с обязательным `fw`, см. §10.2) |
| Добавить новый вариант параметра (новая строка с тем же `id`, новое `condition`), не меняя существующих | в существующий шаблон (с `fw`) |
| Расширить набор значений существующего параметра (`enum`, `min`/`max`) | в существующий шаблон (fw-вариант, см. §9.4) |
| Изменить или удалить существующее значение `enum`, сузить диапазон | новый шаблон под новую прошивку |
| Изменить существующий `condition` | новый шаблон под новую прошивку |
| Изменить адрес, тип, формат существующего элемента | новый шаблон под новую прошивку |
| Удалить канал или параметр | новый шаблон под новую прошивку |

Все строки «новый шаблон под новую прошивку» подразумевают, что изменение обусловлено выпуском новой версии прошивки устройства. Если требуется изменить шаблон **без** изменения версии прошивки (например, исправить ошибку в самом шаблоне) — применяется отдельный путь с суффиксом `-tpl<N>` (см. §10.4); это редкая операция.

**Признак применения настоящего раздела:** для всего шаблона задана минимальная версия прошивки в блоке `hw[].fw` (т. е. шаблон применим только к устройствам с прошивкой не ниже указанной).

**Соглашение:**

- к `device_type` добавляется суффикс `-fw<N.M>`, где `<N.M>` — минимальная версия прошивки;
- имя файла шаблона образуется из `device_type` по формуле §4.4 — суффикс `-fw<N.M>` присутствует и в нём;
- в `hw[].fw` указывается фактическая минимальная версия прошивки.

**Пример** (вымышленное устройство; файл `config-wb-example-fw2.0.json.jinja`):

```jsonc
{
    "device_type": "wb-example-fw2.0",
    "hw": [
        {
            "signature": "WB-EXAMPLE",
            "fw": "2.0.0"
        }
    ],
    ...
}
```

**Покрытие версий прошивок.** Для каждой версии прошивки устройства, с которой оно выпускалось, должен существовать ровно один **валидный (не помеченный `deprecated`) шаблон**, подходящий по сигнатуре и `hw[].fw`. При сканировании устройств выбирается шаблон с максимальным `hw[].fw`, не превышающим фактическую версию прошивки устройства.

При выпуске шаблона для новой прошивки старый шаблон (для устройств с более ранней прошивкой) `deprecated` **не помечается** — иначе сломается поиск шаблона при сканировании устройств со старой прошивкой. Старый шаблон остаётся валидным, его задача — обслуживать устройства с прошивкой ниже `<N.M>`.

Несколько прошивочных ревизий могут сосуществовать:

- `config-wb-example.json.jinja` с `device_type: "wb-example"` — для устройств без `fw`-привязки;
- `config-wb-example-fw2.0.json.jinja` с `device_type: "wb-example-fw2.0"`;
- `config-wb-example-fw3.0.json.jinja` с `device_type: "wb-example-fw3.0"`.

Все они валидны; драйвер выбирает подходящий по сигнатуре устройства и фактической версии его прошивки.

### 10.4 Маркер deprecated

Шаблон помечается как `deprecated`, когда его нужно убрать из списка выбора в каталоге веб-конфигуратора и из поиска при сканировании устройств:

- в имя файла добавляется суффикс `-deprecated`: `config-<device>-deprecated.json[.jinja]`;
- в верхнем уровне шаблона устанавливается `"deprecated": true`.

Драйвер продолжает обрабатывать **существующие конфигурации**, использующие deprecated-шаблон, но новые устройства через него не добавляются.

**Когда помечать deprecated:**

- шаблон полностью заменён более новым с совместимыми именами топиков (миграция конкретного устройства).

**Когда НЕ помечать deprecated:**

- при выпуске нового шаблона для новой версии прошивки старый шаблон **остаётся валидным** для устройств с более ранней прошивкой (см. §10.3).

Маркер `deprecated` совместим с прошивочным суффиксом `-fw<N.M>` — например, `config-wbe2-i-opentherm-fw1.3-deprecated.json` для устаревшего шаблона прошивки 1.3.

#### Замена шаблона без изменения версии прошивки (`-tpl<N>`)

Редкая операция. Применяется, когда нужно внести обратно-несовместимые изменения в шаблон, **не связанные** с выпуском новой прошивки устройства (например, исправление ошибки в самом шаблоне). Привязка к версии прошивки при этом не меняется.

Для исходного шаблона `device_type` сохраняется без изменений (чтобы не сломать существующие конфигурации); в имя файла добавляется суффикс `-deprecated`, в верхнем уровне шаблона устанавливается `"deprecated": true`.

Для нового шаблона (заменяющего deprecated) в `device_type` и в имя файла добавляется суффикс `-tpl1`/`-tpl2` и т. д.

Пример:

| Сущность | Изменение в существующем шаблоне | Значение для нового шаблона |
| --- | --- | --- |
| `device_type` | `"wb-mr6c-v3"` (остаётся без изменений) | `"wb-mr6c-v3-tpl1"` |
| Имя файла | меняется на `config-wb-mr6c-v3-deprecated.json.jinja` | `config-wb-mr6c-v3-tpl1.json.jinja` |

### 10.5 Использование Jinja

**Когда применять `.json.jinja`.** Расширение `.json.jinja` обязательно для шаблонов с повторяющимися блоками каналов или параметров (многоканальные счётчики, многоканальные модули I/O, частотные преобразователи с группами уставок). Ручное дублирование таких блоков в чистом JSON ведёт к рассинхронизации при правках и затрудняет ревью. Для шаблонов без повторяющихся блоков допустим обычный `.json`.

**Инклюды Jinja.** Инклюды применяются только для сущностей, удовлетворяющих **обоим** условиям:

1. сущность объявлена канонической в WB-STD-001 §6;
2. сущность фактически повторяется в трёх и более шаблонах.

Типичные случаи, удовлетворяющие обоим условиям:

- служебные каналы (`sn`, `fw`, `uptime`, `hw_batch`, `t_mcu`, `v_mcu`, `v_vin`, `v_min_vin`, `v_min_mcu`, `t_max_mcu` — см. WB-STD-001 §6.1);
- счётчики нажатий на дискретные входы (`count_<этикетка>`, `count_single_<этикетка>`, `count_long_<этикетка>`, `count_double_<этикетка>`, `count_shortlong_<этикетка>` — см. WB-STD-001 §6.3).

Инклюды для device-specific блоков (произвольные группы регистров конкретной модели) не допускаются — приводят к скрытым зависимостям между шаблонами и ломаются при первой же правке снаружи.
